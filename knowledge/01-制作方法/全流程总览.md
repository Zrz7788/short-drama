这是整条产线的地图。**脚本做什么写在 README，这里写为什么这么设计。**

## 三个关键设计决定

### 1. 实体出图排在分镜之前

常见顺序是「剧本 → 分镜 → 提取实体」。我们刻意把实体和出图提到分镜前面：

- **分镜的每个镜头都要引用实体**（谁、在哪、什么道具）。先出分镜再提取，就得回头
  给 20 个镜头补绑定
- **提示词质量取决于你是否已经看到并锁定了视觉方向**。先写 20 条提示词，
  再发现定妆照的色调不对——全部返工

代价是：实体分级和出图变成分镜的阻塞项。收益是省掉一整轮返工。

### 2. 首帧图是独立阶段，且是最后一个便宜关卡

**这是整条流程性价比最高的一环。** 首帧图约 ¥0.2/张，视频约 ¥4–5.8/条，
差着 **20–30 倍**。

原来的流程从「三视图」直接跳到「生成视频」，中间缺了首帧图。后果是：
一致性最差的纯文生视频只能靠抽卡硬碰，而每次失败要花视频的钱。

正确打法：**在首帧图上抽 10 次（¥2）选最好的一张，再去生视频**——
比视频抽 3 次（¥12–17）又便宜又稳。

首帧图还是**最后一个能便宜返工的环节**。首帧不对就别去烧视频了。

### 3. 提示词定稿不走 LLM，做确定性拼接

第 6 阶段刻意不调用任何模型。理由只有一条：

> 实体的外观描述块必须**逐字复制**进每个镜头的提示词。一旦让模型"润色"，
> 同一个人在不同镜头里就会被描述成不同的人——**这正是跨镜头崩脸的起点**。

代价是提示词读起来不如人写的顺。收益是跨镜头逐字一致、完全可复现、零成本。
脚本对这一点做了**机械校验**：任何实体描述没原样出现就立刻报错。

## 返工成本的分层

整条流程的设计围绕一个事实：**返工成本差两个数量级**。

| 在哪发现问题 | 返工成本 |
|---|---|
| 剧本 | 还没花钱 |
| 定妆照 / 首帧图 | ¥0.2/张 |
| 视频 | ¥4–5.8/次 |
| **成片才发现不一致** | **全部重来** |

原则：**在便宜的地方多卡关，在贵的地方少返工。**
所以上表里带「人工确认」的环节，一个都不该省。

## 实体分级：决定出图量

| tier | 出图 | 判据 |
|---|---|---|
| `main` | 定妆照 + 三视图（4 张） | 是否需要在多个镜头里保持长得一样 |
| `secondary` | 只出定妆照（1 张） | |
| `background` | 不出图 | 路人、一次性道具 |

提取出来的实体里，大量是"路人甲""桌上的杯子"。给它们全出图是纯浪费。
**这一步能把出图量砍掉一半以上**，而它只是分级时多想一秒钟的事。

## 视频生成的三段式

| 模式 | 处理谁 | 分辨率 | 用途 |
|---|---|---|---|
| `draft` | `strategy='draft'` | 480p 样片 | 便宜地多抽 |
| `direct` | `strategy='direct'` | 1080p | 空镜/背影，不值得抽 |
| `final` | 有样片的镜头 | 1080p | 每镜只出一次 |

**把选择留在便宜的那一段。** 一键到底会把"挑哪一条"这个动作挤到贵的阶段去做。

镜头级的 `strategy` 由第 5 阶段决定：正脸特写抽 4–6 次，空镜直出 1–2 次。

## 还没验证的部分

诚实列出——这些只有插上 `ARK_API_KEY` 才能确认：

- **视频任务的响应结构**没对着真实服务验证过。解析是防御式的：
  取不到预期字段就把原始响应落盘到 `.tools/ark-debug/` 并在报错里给出路径
- **Draft 成片的关联字段名**（`ark.DRAFT_REF_FIELD`）是推测值。官方只说
  "通过样片对应的 ID 发起成片生成"，没公布字段叫什么
- 各模型的**真实单价**中，只有 2.5（¥1.45/秒）和 2.0 pro（¥1.00/秒）是你从控制台
  抄来的；Draft 样片的 ¥0.26/秒 是我用官方省费口径反推的
- 抽卡命中率、4 秒够不够完成一个动作、钩子放第几秒流失最少——这些
  `01-制作方法/` 里的假设，都要等真实项目跑完回流到 `04-复盘/`

## 怎么验

```powershell
python tools\verify.py              # 全量验收（含四组自检）
python pipeline\selftest_e2e.py     # 全链路：数据从剧本流到成片，产出真 MP4
```

`selftest_e2e.py` 用本地假服务跑完整十个阶段，并校验成片时长、账目、视图可用性。
它是"这条管线是通的"最有力的证据——**但它没有证明真实 API 能用**。
