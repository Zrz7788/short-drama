# 技能路由的三种误选（jiucaihezi-app 的实战复盘）

> **出处**：`github.com/xusu-ai/jiucaihezi-app` 的提交
> `3216921369baad0abe8252424f09a7b2a72c5a3f`
> `fix(memory): @Jev 规则匹配只信 triggers、长词优先，修掉三处真实误选`
>
> **这份笔记的价值在于：它记的是"一个看起来能用的功能，实际在悄悄地选错"。**
> 我们存在**完全相同的隐患**（见 §五）。

---

## 一、故障现场

用户说：**「把上面的提示词翻译成中文，放入 Wiki 里」**
→ 系统把它**误挂到 `jc-gaibian-silu`（改编思路）技能上**，注入了一整份不相干的 SKILL.md。

三个**互相独立**的缺陷叠在一起造成这个结果。

---

## 二、缺陷一：截断造出假关键词

**候选描述在候选阶段被按 80 字硬切。**

`jc-gaibian-silu` 的描述被切成：

```
…产出并维护 wi
```

**那个 `wi` 命中了消息里的「Wi**ki**」。**

### 修法

> 截断**是提示词排版的事**，放在 `buildDecisionPrompt` 里按分隔符切。
> **候选数据不再截断。**

```js
const CLIP_SEPARATORS = ['、', '，', '；', '。', ' ', '：', ':', '\n']

function clipForPrompt(value, limit = CLIP_LIMIT) {
  const text = normalizeTermSource(value)
  if (text.length <= limit) return text
  const head = text.slice(0, limit)
  const cut = Math.max(...CLIP_SEPARATORS.map(s => head.lastIndexOf(s)))
  // cut 是分隔符自身的位置，+1 才把它留下，否则会切到半个词的尾巴上。
  return `${cut >= limit / 2 ? head.slice(0, cut + 1) : head}…`
}
```

### ⭐ CLIP_LIMIT 是**实测**出来的，不是拍的

> 实测 `~/.agents/skills` 的 **47 条描述最长 317 字、全量合计才 5,586 字**，
> 所以 **400 字等于"不截断"**，同时挡掉异常超长描述把 prompt 撑爆。
>
> **曾经设 80 字**：只有 **8/47** 条能完整保留。
> `jc-juben-yingyi` 结尾的「**只做中译英，不改剧情**」被切掉，
> 模型据此以为它**也支持反向**——**而路由恰恰需要这类限定条件**。

**教训**：截断阈值要按真实数据分布定，**并且不能切出半个词**。

## 三、缺陷二：拿散文描述做子串匹配

`jc-daxi`（打戏）的描述里有「**剧情、人物、场景**」，
于是 **「生成一张人物照片」把打戏 Skill 挂上来了**。

### 修法：**只信 `triggers`**

> `triggers` 是**作者手写的搜索关键词**（`types/skill.ts` 的注释就是这么定的）；
> **描述是写给人看的散文**，拿它做子串匹配会捞出泛词。

具体做法是**故意不给匹配器 description**，让词表只剩 triggers 与名字：

```js
selectedSkill: { id: candidate.id, name: candidate.label, triggers: candidate.triggers },
// 故意不给 description 与 skillContent
```

### ⭐ 代价是**算过的**

> **代价是没写 triggers 的 Skill 规则层看不见，会落到 LLM provider——那比猜错便宜。**

**这句判断很关键**：宁可漏（交给 LLM 判），**不要错**（强制挂一份不相干的 SKILL.md）。

## 四、缺陷三：按命中条数排序，而不是按具体程度

「帮我写一个**短剧剧本**」时：

| 技能 | 命中 | 条数 |
|---|---|---|
| `jc-duanju` | 「**短剧剧本**」 | 1 |
| `jc-daoyan-fenjing` | 「剧本」 | 1 |

**都是 1 条** → 只比条数就按**目录顺序**定胜负 → **选了导演分镜。**

### 修法：长词优先

```js
/** 先比命中的最长词（越具体越可信），再比命中条数。 */
function specificity(terms) {
  return Math.max(...terms.map(t => t.length)) * 10 + terms.length
}
```

## 五、⭐ 我们还查出两个附带的、同样重要的修正

### 5.1 弱命中剔除：ASCII 要整词，CJK 保持子串

```js
function isMeaningfulMatch(term, userRequest) {
  // CJK 没有词边界，保持子串判断（「剧本」就该命中「短剧剧本」）
  if (!/^[\x20-\x7e]+$/.test(term)) return true
  // ASCII 词必须整词命中：`wi` 不能命中 `Wiki`，`use` 不能命中 `useful`
  return new RegExp(`(^|[^A-Za-z0-9_])${escaped}($|[^A-Za-z0-9_])`).test(userRequest)
}
```

> **ASCII 与 CJK 必须分开处理。** 一刀切用子串会在英文上炸，一刀切用整词会在中文上失效。

### 5.2 提示词要写「宁缺勿滥」

改前的措辞：
> `3. skills 最多 1 个；只有一个 Skill 能真正完成这件事才选它。`

改后：
> `3. skills 最多 1 个，而且**必须真有一款 Skill 是为这件事设计的。
> 只是"沾边"、只是话题相同（如提到剧本），都不算**——选错会强制挂上一整份不相干的 SKILL.md。`
> `4. **没有任何一款合适就留空，直接回答反而更好，这是允许的答案。**`

**"留空是允许的答案"** 这句是重点——不写，模型会倾向于勉强选一个。

## 六、⚠️ 我们有同样的隐患，而且更严重

排查了我们自己的技能库：

| 项 | 我们 | jiucaihezi |
|---|---|---|
| 有 `triggers` 的技能 | **1 / 20**（只有从 OpenMontage 来的 `ffmpeg`） | 作者手写 |
| 描述最长 | **1930 字** | 317 字 |
| 描述里含泛词的技能 | **6 个**（最多的含 **10 个**泛词） | 1 个（`jc-daxi`） |

**泛词污染排行**（这些词本身不指向任何一个技能）：

| 技能 | 泛词数 | 命中的泛词 |
|---|---|---|
| `ai-mandrama-pipeline` | **10** | 人物、分镜、剧本、剪辑、场景、模型、生成、短剧、视频、角色 |
| `short-drama-image-prompts` | 8 | 人物、图片、场景、提示词、生成、短剧、角色、风格 |
| `short-drama-assets` | 8 | 人物、剧本、图片、场景、提示词、生成、短剧、角色 |
| `short-drama-video-prompts` | 6 | 人物、分镜、提示词、生成、短剧、视频 |

**如果路由按描述做子串匹配，任何提到「剧本」「人物」「场景」的请求都会命中第一个。**
——这正是 `jc-daxi` 那个 bug 的形状。

**而且我们的描述长度是他们的 6 倍**：若按 80 字截断，后果比他们严重得多。

## 七、应该怎么做

| 我们的现状 | 应该改成 | 依据 |
|---|---|---|
| 20 个技能里 19 个没有 `triggers` | **给每个技能写 `triggers`**——作者手写的具体搜索词，**不要用泛词** | §三 |
| 描述里塞了 10 个泛词 | 泛词**从描述里拿掉**（描述是给人看的散文，不该当匹配源） | §三 |
| `install_skill.py` 不检查 triggers | **加软门禁**：没有 `triggers` 的技能提示"规则层看不见它" | §三 |
| 没有"长词优先"的概念 | 若将来自己做路由：**`specificity = 最长命中词 × 10 + 条数`** | §四 |
| 可能按 80 字截断描述 | **截断只在渲染时做，且按分隔符切，不切半个词**；阈值按真实数据分布定 | §二 |
| 提示词没写"宁缺勿滥" | 加：**只是"沾边"不算；没有任何合适就留空，这是允许的答案** | §5.2 |

## 八、这份复盘最值得学的地方

**它记的不是"我们加了个功能"，而是"一个看起来能用的功能在悄悄选错"。**

三个缺陷**各自单独看都不致命**：
- 截断到 80 字，看起来是省 token 的好习惯
- 拿描述做匹配，看起来比只看 triggers 信息更全
- 按命中条数排序，看起来公平

**但它们叠起来，就让一个翻译请求挂上了改编思路。**

而且**故障现象是"选错了"，不是"报错了"**——没有异常、没有日志、没有测试失败。
**只有用户实测才发现。**

> **这与我们在流水线里反复踩到的是同一件事**：
> db 自检一直在验证一个已废弃的方案、三个自检用着已弃用模型的价格——
> **都是"能跑通但结果是错的"，都是安静地坏着。**
