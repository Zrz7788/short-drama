# 项目档案

每部剧一个文件，命名 `剧名.md`。从下面的模板复制。

建档后同步在数据库里建 `project` 记录：

```sql
INSERT INTO project (name, logline, genre, target_episode_seconds)
VALUES ('剧名', '一句话故事', '悬疑', 80);
```

## 领域事实

**这一章是本目录最重要的部分。** 故事发生在哪个职业、哪个行业、哪个具体场所，
就把那个领域的真实情况写在这里。**它是所有 location / prop 实体的上游。**

> **为什么必须单独有这一章**：第 1 集曾把「冷柜间」写成化妆间的别名，又把冷柜、
> 转运推车、化妆台塞进同一间屋，结果**空间、载体、动作三样全错**，而模型只是
> 忠实地画了出来。根因不是模型，是**现场凭想象编了一个职业的常识**。
> 实体描述是生图提示词的**直接输入**，错了每张图 ¥0.30，所以必须在这里先立住。

**领域事实是「一部剧一次」，不是「每集一次」**——60 集都在同一个殡仪馆，
研究一次全剧共用。**没有这一章就不许进第 3/4 阶段出图。**

## 两条纪律

1. **角色技术设定只在数据库里维护。** 本目录的文件写创作意图和设定背景，
   `ref_image_path`、`seed`、`voice_id` 这些一旦两处都写就会漂移，最后没人知道哪个是对的。

2. **「领域事实」每一条都要有出处和置信度；写不出出处的标 `低` 并注明"待验证"。**
   宁可标"待验证"也不要编一个像真的——**编出来的会被下游当成事实用**。
   知识库总则第一条（无出处的数字/事实不写成定论）在这里同样适用。

## 和流水线怎么连

| 环节 | 怎么用 |
|---|---|
| 第 0 阶段（spec） | 产出 `project_brief`，即本目录的 `<剧名>.md` |
| 第 2 阶段（cast） | 每个 location / prop 实体必须填 `entity.domain_fact`，指回上表的编号（如 `F-01`）；**指不回去就阻断，不许出图**。人物与纯剧情道具填 `story` |
| 第 3/4 阶段（art） | 出图前先过第 2 阶段那道门禁，所以领域事实一错就会在花钱前被拦 |

`entity.domain_fact` 的取值约定：

- `F-01` / `F-02` … —— 指回本章某一条
- `story` —— 显式声明"这是剧情设定，不需要领域事实"（人物、一封信、一张化验单）
- **留空 = 错误**。留空分不清"不需要"和"忘了填"，所以必须显式写 `story`。
